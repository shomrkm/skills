# spec-design-proposal

仕様・デザインの検討で、意思決定できる状態の比較資料を作る。

## 責務

**やること**: 業務フローとユースケースを理解し、前提を確定させ、検討の軸を絞ったうえで最大3案を作り、アーティファクトとして公開する。

**やらないこと**:
- 実装 (案が決まったあとの実装は別タスク)
- 案を勝手に1つに決めること (推奨は示すが、決めるのは利用者)
- 調べればわかることを利用者に聞くこと、調べてもわからないことを推測で埋めること

## 必ず対話モードで実行する

このスキルは利用者との対話を前提とする。前提条件の確認とヒアリングを飛ばすと、的外れな案を3つ並べるだけになる。

スケジュール実行などで応答する人がいない場合は、作業せずに「対話が必要」と報告して終了する。

## ワークフロー

```
- [ ] 1. お題を把握する
- [ ] 2. 自分で調べる (業務フロー・ユースケース・既存実装)
- [ ] 3. 調べてもわからないことをヒアリングする
- [ ] 4. 前提条件を確定させ、変数を減らす
- [ ] 5. 案を作る (3つ以内)
- [ ] 6. モックとプロトタイプを作る
- [ ] 7. アーティファクトにまとめて公開する
- [ ] 8. フィードバックを反映する
```

### 1. お題を把握する

最初に、検討対象と「何を決めたいのか」を1〜2文で言い直して利用者に確認する。

- 決めたいのは仕様 (振る舞い・データ・権限) か、デザイン (画面構成・操作) か、その両方か
- 誰が、いつまでに、何のためにこの検討結果を使うか (チームの議論用、PdM への提案、デザインレビュー前の叩き台など)

ここが曖昧なまま進めない。

### 2. 自分で調べる

ヒアリングの前に、調べられることは調べる。利用者の時間を「調べればわかること」に使わせない。

調べる対象と観点は `references/discovery.md` に従う。最低限、以下を把握する。

- **業務フロー**: 誰が、どの順番で、何をきっかけに、何をする業務か
- **ユースケース**: 主要なアクターと、それぞれが達成したいこと
- **既存実装**: 関連する画面・モデル・API・権限 (作業ディレクトリのリポジトリを読む)
- **既存 UI**: 似た画面やコンポーネントがリポジトリにあるか (手順 6 のスタイル参照にも使う)

調べた結果は「わかったこと」「推測したこと」「わからないこと」に分けてメモしておく。推測は推測として扱い、事実と混ぜない。

### 3. 調べてもわからないことをヒアリングする

手順 2 の「推測したこと」「わからないこと」のうち、**案の分岐に効くものだけ**を AskUserQuestion で聞く。

- 1回の質問は最大4問。選択肢には調べた結果から考えられる候補を入れ、推奨があれば先頭に置く
- 質問文には「なぜそれを聞くのか (どの判断に効くのか)」を短く添える
- 一度に全部聞こうとせず、答えによって次の質問が変わるなら分けて聞く

聞く観点は `references/discovery.md` の「ヒアリング観点」を使う。

### 4. 前提条件を確定させ、変数を減らす

案を作る前に、検討の土台を利用者と合意する。手順は `references/narrowing.md` に従う。

1. **確定している前提条件**を一覧にする (仕様上の制約、技術的制約、スコープ外、既に決まっている方針)
2. **検討の変数** (案によって変わりうる設計判断) を洗い出す
3. 前提・既存パターン・業務上の必然から**固定できる変数を固定**する。固定した理由も書く
4. 残った変数のうち、案の違いを生む**主軸を1〜2本**に絞る

ここまでの結果を利用者に提示し、合意を取ってから次へ進む。前提が覆ると案がすべて無駄になるため、この確認は省略しない。

### 5. 案を作る (3つ以内)

主軸に沿って、互いに本質的に違う案を作る。作り方と書き方は `references/narrowing.md` の「案の作り方」に従う。

- 案は最大3つ。主軸が1本で選択肢が2つしかないなら2案でよい。水増しのための3案目は作らない
- 各案に「どのユースケースに強いか / 弱いか」「前提条件をどう満たすか」「実装コストとリスク」を書く
- 推奨案を1つ選び、理由を書く

### 6. モックとプロトタイプを作る

各案に画面モックを付ける。操作してみないと違いが伝わらない案には、操作できるプロトタイプを埋め込む。判断基準と作り方は `references/artifact-guide.md` に従う。

**スタイルは smarthr-ui に寄せる。** 手順は `references/smarthr-ui-style.md` に従う。

1. 作業ディレクトリのリポジトリに、smarthr-ui を使った類似画面や独自コンポーネントがないか探す
2. 見つかったら、そのレイアウト・コンポーネントの組み合わせ・文言のトーンをまねる
3. なければ `assets/smarthr-ui-like.css` のクラスで組む

### 7. アーティファクトにまとめて公開する

`assets/proposal-template.html` を土台に、1枚の HTML にまとめる。構成は `references/artifact-guide.md` の「ページ構成」に従う。

公開は Artifact ツールで行う。書く前に `artifact-design` スキルを読み込み、ページの契約 (タイトル、ダークモード、外部スクリプトの読み込み元など) を守る。

公開したら URL を利用者に伝え、どの案を推すか・何を決めてほしいかを一言添える。

### 8. フィードバックを反映する

利用者のフィードバックで前提や変数が変わったら、手順 4 から見直す。同じファイルパスで再公開して URL を保つ。

## 避けるべき間違い

- ❌ 業務フローを理解しないまま画面から考え始める
- ❌ 調べればわかることを利用者に聞く / わからないことを推測で埋めて事実のように書く
- ❌ 前提条件の合意を取らずに案を作る
- ❌ 変数を減らさずに案を作る (案同士の違いが何なのか説明できなくなる)
- ❌ 見た目だけ違う案を並べる (案の違いは主軸の違いであること)
- ❌ 4案以上出す / 3案に揃えるために弱い案を足す
- ❌ 操作の違いが論点なのに静止画だけで比較する
- ❌ smarthr-ui にないコンポーネントや独自の配色を、理由なく持ち込む
- ❌ リポジトリに既存の類似画面があるのに無視して一から組む
