# 前提条件の確定・変数の削減・案の作り方

案を作る前に検討の自由度を減らす。自由度が大きいまま案を作ると、案同士が何で違うのかを説明できず、比較しても決められない。

## 1. 確定している前提条件を一覧にする

次の4種類に分けて書く。それぞれに出典 (資料、コード、利用者の回答) を付ける。

| 種類 | 例 |
|---|---|
| 仕様上の制約 | 評価期間中は評価シートの項目を変更できない |
| 技術的制約 | 既存の API はページングのみ対応で、全件取得はできない |
| スコープ外 | モバイル対応は今回やらない |
| 決定済みの方針 | 一覧画面から詳細へはページ遷移で移動する (既存画面と揃える) |

前提が少なすぎると感じたら、ヒアリングに戻る。

## 2. 検討の変数を洗い出す

案によって変わりうる設計判断を列挙する。よく出る変数:

- **情報設計**: 1画面に何を出すか、どこで分割するか
- **操作の単位**: 1件ずつか一括か、即時反映か保存ボタンか
- **画面遷移**: ページ遷移 / ダイアログ / インライン編集 / サイドパネル
- **状態と権限**: どの状態で誰が何をできるか
- **データの持ち方**: 新しい概念を足すか、既存の概念で表現するか
- **段階的な導入**: 最小構成で出して後から足すか、最初から揃えるか

## 3. 固定できる変数を固定する

次のいずれかに当てはまる変数は、案の比較対象にせず固定する。

- 前提条件から一意に決まる
- プロダクト内に既存のパターンがあり、外す理由がない
- 業務フロー上、選択の余地がない (例: 承認が必要な業務で即時反映はできない)
- どちらを選んでも主要ユースケースへの影響が小さい

固定した変数は「固定した判断」として理由とともにアーティファクトに載せる。読み手が「なぜこの案にはこれがないのか」と迷わないようにするため。

## 4. 主軸を1〜2本に絞る

残った変数のうち、主要ユースケースへの影響が大きいものを主軸にする。

- 主軸1本: 主軸上の選択肢がそのまま案になる (2〜3案)
- 主軸2本: 2軸の組み合わせから、意味のある組み合わせを最大3つ選ぶ
- 主軸が3本以上残る: まだ絞れていない。ヒアリングで優先度を聞くか、段階を分けて検討することを提案する

ここまでを利用者に提示して合意を取る。

## 案の作り方

### 案の条件

- 主軸上ではっきり違う。見た目 (配色・配置の微調整) だけの違いは案にしない
- すべての前提条件を満たす。満たせない案は出さない (出すなら「前提を変えれば可能な案」と明示する)
- 主要ユースケースを一通り遂行できる

### 各案に書くこと

| 項目 | 内容 |
|---|---|
| 一言で | 案の特徴を1文で (例: 「一覧上でその場で編集する」) |
| 主軸での立ち位置 | 主軸のどの選択肢を取ったか |
| 業務フローの流れ | 主要ユースケースを、この案だとどう操作するか |
| 強いユースケース / 弱いユースケース | 誰のどの場面に向くか、向かないか |
| 実装コストとリスク | 既存実装への影響、新規に必要なもの、懸念点 |
| 未解決の論点 | この案を選んだら次に決めるべきこと |

### 推奨案

推奨を1つ選び、「どの前提とユースケースを重視したからこれを選んだか」を書く。推奨しない案にも、選ぶべき状況を書く (例: 「将来 一括操作が主になるなら案Bが良い」)。

### 書き方

- 案の名前は「案A: 〜」のように記号と特徴の組にする。「シンプル案」「リッチ案」のような程度の名前は避ける
- 比較表を1つ作り、主軸と評価観点を行、案を列にする。評価は ◎/○/△ ではなく短い言葉で書く
