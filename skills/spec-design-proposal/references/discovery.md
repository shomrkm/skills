# 業務フロー・ユースケースの理解とヒアリング

## 自分で調べる対象

上から順に、得られる情報が多いものから当たる。

| 対象 | 見るもの | わかること |
|---|---|---|
| 利用者が渡した資料 | PRD、Issue、Slack スレッド、議事録、Figma の説明文 | 背景、要求、決まっていること |
| 作業ディレクトリのリポジトリ | ルーティング、画面コンポーネント、モデル、権限定義、i18n の文言 | 既存の業務フロー、データ構造、用語 |
| 関連する既存画面 | 同じ業務の前後の画面、似た操作をする画面 | 操作の慣習、再利用できる UI |
| ドキュメント | README、`docs/`、ADR、ヘルプページ | 設計意図、過去の判断 |
| 接続されたツール | Notion、Google Drive、Slack など (使えるときだけ) | 仕様書、過去の議論 |

### リポジトリの調べ方

- 画面名・機能名・ドメイン用語で検索し、ルーティング → ページコンポーネント → 子コンポーネントの順に辿る
- Rails なら `config/routes.rb`、モデル、Policy / 権限まわり、関連する API (serializer や GraphQL type) を読む
- i18n の文言ファイルは、プロダクト内の用語と言い回しを知るのに使える。案の文言はこれに合わせる
- テスト (request spec、E2E) は、想定されている業務シナリオを知る手がかりになる

## 整理する観点

### 業務フロー

- アクター (誰が関わるか。例: 評価者、被評価者、人事担当者、管理者)
- きっかけ (何が起きたらこの業務が始まるか。期間の開始、通知、他者の操作など)
- ステップと順序 (誰が何をして、次に誰に渡るか)
- 分岐と例外 (差し戻し、代理入力、期限切れ、途中での異動・退職など)
- 頻度と量 (年に1回か毎日か、1人あたり何件扱うか)

フローは箇条書きか簡単なシーケンスで書く。アーティファクトにも載せる。

### ユースケース

アクターごとに「〜したい。なぜなら〜」の形で書く。主要なもの (業務の大半を占めるもの) と、少数だが重いもの (管理者の一括操作、例外対応など) を区別する。

### 既存実装の制約

- データ構造上できないこと、変更コストが高いこと
- 権限モデル
- 既存画面との一貫性で守るべきこと

## ヒアリング観点

調べてもわからず、かつ案の分岐に効くものだけを聞く。

| 観点 | 例 |
|---|---|
| 目的 | この変更で解決したい一番の課題は何か。成功をどう判断するか |
| 対象ユーザー | 主に使うのは誰か。ITリテラシーや利用頻度に偏りはあるか |
| スコープ | 今回やらないと決めていることはあるか。段階リリースの予定はあるか |
| 制約 | 期限、工数、触れない既存仕様、法令・社内ルール |
| 優先度 | 速さと正確さ、一覧性と詳細の見やすさ、などトレードオフのどちらを取るか |
| 決定済みの方針 | PdM・デザイナーと既に合意していることはあるか |
| 例外ケース | 調べて見つかった例外ケースを、今回考慮するか |

### 聞き方

- 選択肢は「調べた結果から考えられる候補」で作る。白紙で聞かない
- 推測が立っているなら「〜と理解しているが合っているか」と確認の形にする
- 答えによって次の質問が変わるなら、分けて聞く
