# project-digest

GTD の Project の状況を集約し、進捗サマリと次の一手の提案を作る。

## 責務

**やること**: タスクの状況から Project の状態を判定し、サマリと提案を組み立てる。

**やらないこと**:
- Notion の読み書きの手順を持つこと → `shomrkm-notion` スキルに委譲する
- Slack の投稿先や書式を持つこと → `shomrkm-slack-notify` スキルに委譲する
- 提案を実行すること (後述の「提案に留める」)

## 実行モード

このスキルは手動と無人スケジュールの両方から呼ばれる。**最初にモードを判定すること。**

判定基準: **このターンにユーザーからの直接の発話があるか**。判断がつかない場合は必ずスケジュールモードとして扱う (安全側)。

| | 手動モード | スケジュールモード |
|---|---|---|
| 対象 | 引数指定、未指定なら全アクティブ Project | 常に全アクティブ Project |
| 曖昧なとき | AskUserQuestion で確認 | **質問禁止**。「要確認」としてサマリに含める |
| 提案 | 提示して承認を得る | Slack に出して終了 |
| Slack 通知 | 実行後に通知 | 常に通知 (唯一の出力先) |

スケジュールモードで AskUserQuestion を使うと、応答する人間がいないためスキルが停止する。

## ワークフロー

```
- [ ] 1. 実行モードを判定
- [ ] 2. アクティブ Project とタスクを取得
- [ ] 3. Project ごとに状態を判定
- [ ] 4. 次の一手を組み立てる
- [ ] 5. Progress Summary を更新
- [ ] 6. Slack に通知
```

### 1. 実行モードを判定

上記の基準で判定する。以降の分岐はすべてこれに従う。

### 2. アクティブ Project とタスクを取得

`shomrkm-notion` スキルを使う (DB ID・ビュー URL・クエリ手順はそちらが持つ)。

必要な情報:
- アクティブな Project 一覧 (`status` が `in-progress` / `planning` / `Not started`)
- 各 Project に紐づくタスク (`task_type`, `due_date`, `completed_at`)
- 各 Project ページ本文の `## As-Is` と `## To-Be`

アクティブ Project が 0 件なら、何もせず終了する (Slack にも投稿しない)。

### 3. Project ごとに状態を判定

**判定は機械的に行う。** AI が毎回異なる基準で判定すると、週ごとの比較が無意味になる。上から順に判定し、最初に該当したものを採用する。

| 状態 | 条件 |
|---|---|
| `情報不足` | `To-Be` が空、または紐づくタスクが 0 件 |
| `要判断` | 期限切れタスクが 3 件以上、または `Wait for` が全体の半数以上 |
| `停滞` | 直近 2 週間で `completed_at` が 1 件も入っていない |
| `順調` | 上記いずれにも該当しない |

### 4. 次の一手を組み立てる

判断基準は `references/proposal-rules.md` を Read すること。

### 5. Progress Summary を更新

`shomrkm-notion` スキルを使って、各 Project ページの `## Progress Summary` セクションを更新する (更新手順はそちらが持つ)。

書き込む内容:

```markdown
> 🤖 自動更新: <YYYY-MM-DD>

**進捗**: 完了 <N> / 全 <M> タスク · 期限切れ <K> 件
**状態**: <順調 | 停滞 | 要判断 | 情報不足>

### 直近の動き
- (直近2週間で completed_at が入ったタスク、最大5件)

### 詰まっているもの
- (due_date 超過、または Wait for のまま2週間以上のタスク)

### 次の一手（提案）
- [ ] (提案1)
- [ ] (提案2)
```

該当がないセクションは「なし」と書く。セクション自体は残す (毎回同じ形にして差分を追えるようにするため)。

**`## Progress Summary` 以外のセクションには一切書き込まない。** プロパティ (`status` 等) も変更しない。手動・スケジュールどちらのモードでも同じ。

### 6. Slack に通知

`shomrkm-slack-notify` スキルを使う (チャンネル・書式はそちらが持つ)。ダイジェスト型の書式で、要対応の Project を先頭に置く。

## 提案に留める

**AI は提案を作るところまでを行い、実行しない。**

実行しないものの例:
- タスクを新規作成する
- タスクの `task_type` や `due_date` を変更する
- Project の `status` を変更する
- コードを変更する、PR を作る

手動モードでは、提案を提示した上で shomrkm が承認したものだけを実行する。実行そのものは `shomrkm-notion` スキルなど適切なスキルに委ねる。

スケジュールモードでは、提案を Slack と Progress Summary に出して終了する。

理由: GTD では「次に何をするか」は本人が決める領域。また Project の性質によっては (組織の合意形成や個人の意思決定) AI が進められる余地がそもそも無い。

## エラー処理

無人実行では失敗が誰にも気づかれないため、**失敗も必ず Slack に出す**。

| 失敗 | 振る舞い |
|---|---|
| Notion 読み取り失敗 | 中断し、Slack にエラーを通知 |
| 特定 Project の処理失敗 | その Project をスキップして続行。Slack 末尾に「⚠️ N件スキップ」を付記 |
| Progress Summary 書き込み失敗 | その Project をスキップ扱い。書きかけの状態にしない |
| Slack 投稿失敗 | Notion への書き込みは完了しているのでリトライせず終了 |

Progress Summary は毎回全置換なので、同日に複数回実行しても結果は同じになる (冪等)。

## 避けるべき間違い

- ❌ スケジュールモードで AskUserQuestion を使う (応答する人間がいない)
- ❌ 状態判定を毎回その場の感覚で行う (機械的な基準に従う)
- ❌ `Progress Summary` 以外のセクションやプロパティを書き換える
- ❌ 提案を実行してしまう (提案までに留める)
- ❌ Project ごとに Slack へ個別投稿する (1実行1投稿)
- ❌ DB ID やビュー URL をこのスキル内にハードコードする (`shomrkm-notion` に委譲)
