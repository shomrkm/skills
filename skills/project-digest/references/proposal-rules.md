# proposal-rules.md — 次の一手の判断基準

Project ごとに提案を組み立てるときの可否ライン。

## 目次

- 提案の上限と粒度
- 提案してよいもの
- 提案してはいけないもの
- 状態別の典型パターン

## 提案の上限と粒度

**上限は Project あたり 3 件。** 多いと選べなくなり、GTD の「次の一手は1つ」原則に反する。

**粒度の基準: そのまま Tasks DB の `Name` にできるか。** できないものは抽象的すぎるので却下する。

| | 例 |
|---|---|
| ❌ 却下 | 「ペルソナ運用を前に進める」 |
| ✅ 採用 | 「ペルソナ草案をチームの定例で共有してFBをもらう」 |
| ❌ 却下 | 「Vite 移行を進める」 |
| ✅ 採用 | 「utsuwa の vite.config.ts を作る」 |

判定に迷ったら「これを読んだ shomrkm が、明日そのまま着手できるか」を問う。

## 提案してよいもの

**次に取るべき具体的な行動が1つに定まるもの**に限る。

1. **到達可能な次のアクション** — 現在の状態から直接着手できるもの
2. **`To-Be` と現状のギャップから導ける、まだタスク化されていない行動** — Project ページに書かれた目指す状態を根拠にする
3. **期限切れタスクの再スケジュール、または `Someday / Maybe` への降格** — 期限切れが溜まっている Project で有効
4. **`To-Be` が空の Project に対する「To-Be を書く」提案** — 情報不足の状態では、まずこれが唯一の正しい提案になる

## 提案してはいけないもの

1. **本人の意思決定そのもの**
   - 「このプロジェクトを閉じては？」「優先度を下げては？」
   - 理由: GTD では Project を続けるか畳むかは本人が決める領域。AI が踏み込むべきでない

2. **実行に踏み込む提案**
   - 「PR を作りました」「タスクを追加しておきました」
   - 理由: このスキルは提案までに留める

3. **根拠が Notion 上に存在しない一般論**
   - 「テストを書きましょう」「ドキュメントを整備しましょう」
   - 理由: Project の `As-Is` / `To-Be` / タスクのいずれにも根拠がない提案は、AI の一般論でしかなく shomrkm の文脈に合わない

4. **精神論・励まし**
   - 「引き続き頑張りましょう」「順調です、この調子で」
   - 理由: 行動につながらない

## 状態別の典型パターン

状態判定 (SKILL.md 参照) ごとに、出すべき提案の方向が決まる。

| 状態 | 提案の方向 |
|---|---|
| `情報不足` | まず `To-Be` を書く提案。タスクが 0 件なら最初のタスクを切る提案。**他の提案はしない** |
| `要判断` | 期限切れタスクの再スケジュールまたは降格。`Wait for` が多い場合は、待ち状態の解消につながる行動 |
| `停滞` | 最も小さく着手できるタスクを1つ提示する。動き出しのきっかけを作る |
| `順調` | `To-Be` とのギャップから、まだタスク化されていない次の行動。**無理に出さなくてよい** (提案 0 件も正しい結果) |

`順調` な Project に対して提案を絞り出そうとすると、根拠のない一般論に流れやすい。出すものがなければ「次の一手（提案）」は「なし」でよい。
